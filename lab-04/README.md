Це груба оцінка на створеному тестовому наборі; вона не включає індекси, журнал транзакцій, резервні копії чи інші таблиці.

| Операція, що впирається в межу | Що роблять | Чим платять |
|---|---|---|
| Одночасно підтверджують бронювання того самого ПК на перетинний час | транзакційне блокування/обмеження в PostgreSQL | один запит чекає або отримує відмову |
| Часто відкривають картку місячної виручки | кешують `revenue:2026-03` у Redis | пам'ять кешу й до 5 хвилин застарілого значення |
| Постійно додають бронювання і зберігають історію | архівують старі періоди або партиціюють таблицю | складніше адмініструвати й виконувати звіти |
| Під час втрати зв'язку два вузли приймають бронювання одного ПК | зберігають авторитетний запис на одному вузлі | на ізольованому вузлі операція тимчасово недоступна |

За розрахунком 6.42 MiB на рік, диск не буде першим обмеженням. Першою ризиковою операцією є підтвердження одночасних бронювань на той самий ПК: потрібна серіалізація перевірки й запису, інакше виникне подвійне бронювання.

## 2. Ключ шардингу

У цьому навчальному розгортанні шардинг не вмикався: наявного обсягу для нього замало. Як проектний ключ обрано `{ pc.club.club_id: 1, _id: 1 }`: клубний префікс наближає записи одного клубу до клубних звітів, а друге поле дає поділ бронювань усередині клубу. Запит бронювань за клубом стає дешевшим за глобальний звіт; пошук лише за `_id` без `club_id` може звернутися до кількох shard-ів.

Значення `club_id = 1` (Center) потенційно перекошує дані: у навчальному зрізі це 7 бронювань проти 4 у Riverside і 2 у Campus. Композитний ключ дозволяє ділити діапазон цього клубу за `_id`, але реальний баланс треба підтверджувати вимірюванням. Ключ не змінюють на заповненій базі без плану міграції: доведеться переміщати дані й індекси, витрачаючи ресурси та створюючи ризик затримок.

## 3. Мережевий розділ

Інваріант області: **на одному ПК не можна підтвердити два активні бронювання з інтервалами, що перетинаються**. Уявімо два вузли, між якими розірвано мережу, і однаковий запит на цей ПК приходить до обох.

| Варіант «відмовити» | Варіант «виконати» |
|---|---|
| Вузол без підтвердження від узгодженого джерела відхиляє бронювання | Обидва вузли приймають його локально |
| Інваріант не порушується; частина користувачів не може забронювати місце | Користувачі бачать успіх, але після синхронізації виникає подвійне бронювання |
| Відмову бачить користувач, який потрапив на ізольований вузол | Конфлікт виявляє адміністратор або клієнт під час злиття |
| CP: збережена узгодженість, пожертвувана доступність | AP: збережена доступність, ризик порушити інваріант |

Поки мережа розірвана, вузли не можуть одночасно гарантувати і локальне виконання, і глобальну відсутність конфлікту. Для підтвердження бронювання обрано CP-поведінку: краще тимчасово відмовити, ніж продати одне місце двічі. Перерахунок кешованої виручки витримує остаточну узгодженість; підтвердження бронювання — ні.

## 4. Межа документа

Документом є знімок бронювання, який застосунок показує разом із клієнтом, ПК, клубом, тарифом та оплатою. Такий документ скорочує читання кількох таблиць, але зберігає копії атрибутів.

| Таблиця робочої схеми | Представлення | Причина |
|---|---|---|
| `reservations` | корінь документа | ідентифікує подію |
| `clients` | вкладений `client` | клієнта показують у бронюванні |
| `pcs`, `clubs` | вкладені `pc` та `pc.club` | потрібні місце та клуб |
| `tariffs` | вкладений `pc.tariff` | фіксується тарифний контекст |
| `payments` | вкладений `payment` або `null` | оплата потрібна в тому самому екрані |

```json
{
  "_id": 1,
  "starts_at": "2026-03-01T10:00:00+02:00",
  "ends_at": "2026-03-01T12:00:00+02:00",
  "status": "active",
  "client": {
    "client_id": 1,
    "full_name": "Alice Anderson",
    "phone": "+380000000301"
  },
  "pc": {
    "pc_id": 1,
    "seat_number": 1,
    "club": {
      "club_id": 1,
      "name": "Cyber Club Center",
      "address": "1 Main Street"
    },
    "tariff": { "tariff_id": 1, "name": "Basic", "price_per_hour": 100 }
  },
  "payment": { "amount": 200, "payment_method": "card" }
}
```

Якщо телефон клієнта зміниться, вкладені копії в старих бронюваннях не оновляться автоматично. Це або свідомий історичний знімок, або аномалія — залежно від вимоги. На відміну від реляційної моделі, MongoDB без додаткової валідації не гарантує зовнішні ключі, допустимі статуси чи правильність вкладених полів.

## 5. Колекція

Файл: [load-documents.js](load-documents.js). Колекція `reservations` містить 10 документів — копію бронювань №1–10; початкова робоча таблиця PostgreSQL містить 12 рядків.

У Compass вкладені `client`, `pc`, `club`, `tariff` і `payment` відображаються як окремі об'єкти, а не як текст. Методичка дозволяє опис вигляду колекції; скриншот Compass у репозиторій не додавався.

## 6. Операції над документами

Файл: [operations.js](operations.js).

| Операція | Дія словами | Результат | Відповідник SQL роботи №2 | Відмінність |
|---|---|---|---|
| `insertOne` | додати бронювання №9001 | `insertedId: 9001`, 11 документів | `INSERT INTO reservations (...) VALUES (...)` | один документ може містити вкладені сутності без `JOIN` |
| `find` з `payment: null` | знайти бронювання без оплати | 5 після вставки №9001 | `reservations LEFT JOIN payments WHERE payment_id IS NULL` (2 таблиці) | `NULL` перевіряється у вкладеному полі |
| `find` за `pc.club.name` | знайти бронювання Center | 5 документів | Для такого набору полів «З'єднання 2» роботи №2 об'єднує 6 таблиць | фільтр читає вкладений шлях замість кількох `JOIN` |
| `updateOne` | змінити час завершення №9001 | `matchedCount: 1`, `modifiedCount: 1` | `UPDATE reservations SET ends_at = ... WHERE reservation_id = 9001` | `updateOne` змінює один документ; SQL без унікального `WHERE` може змінити багато рядків |
| `deleteOne` | видалити тимчасовий №9002 | до 12, після 11; `deletedCount: 1` | `DELETE FROM reservations WHERE reservation_id = 9002` | видаляється документ; немає автоматичних реляційних FK-зв'язків |

«З'єднання 2» роботи №2 відновлює ті самі поля з 6 таблиць; умову `club.name = 'Cyber Club Center'` до нього треба додати окремо. `updateOne` змінює не більше одного документа, тоді як SQL `UPDATE` змінює всі рядки, що відповідають `WHERE`; `deleteOne` також не запускає каскадних дій зовнішніх ключів.

## 7. Повторний запис

Повторна вставка `_id: 1` повернула:

```text
E11000 duplicate key error collection: dbsa.reservations index: _id_ dup key: { _id: 1 }
```

Спрацював унікальний індекс `_id_`. Upsert для нового `_id: 10001` дав такі лічильники: до — 11 документів; перший запуск — `matchedCount: 0`, `modifiedCount: 0`, `upsertedCount: 1`, стало 12; другий — `matchedCount: 1`, `modifiedCount: 0`, `upsertedCount: 0`, лишилося 12. Це близько за змістом до `INSERT ... ON CONFLICT`, але MongoDB повідомляє результат через окремі лічильники документа. Без заданого `_id` повторні запуски створювали б нові документи.

| Запуск `updateOne` з `upsert: true` | `matchedCount` | `modifiedCount` | `upsertedCount` | Документів |
|---|---:|---:|---:|---:|
| до запуску | — | — | — | 11 |
| перший | 0 | 0 | 1 | 12 |
| другий | 1 | 0 | 0 | 12 |

Ідемпотентність видно з кількості: після двох запусків існує один документ з `_id: 10001`.

## 8. Агрегація

Файл: [aggregate.js](aggregate.js). Конвеєр за березень повторює показник SQL-запиту №2 роботи №3 — сума оплат за клубом для груп, де сума перевищує 250:

```javascript
[
  {
    $match: {
      starts_at: {
        $gte: ISODate("2026-03-01T00:00:00+02:00"),
        $lt: ISODate("2026-04-01T00:00:00+02:00")
      }
    }
  },
  {
    $group: {
      _id: "$pc.club.name",
      reservation_count: { $sum: 1 },
      paid_amount_sum: { $sum: "$payment.amount" }
    }
  },
  { $match: { paid_amount_sum: { $gt: 250 } } },
  { $sort: { paid_amount_sum: -1, _id: 1 } }
]
```

Результат: Center — 5 бронювань / 1040; Campus — 1 / 300. Числа збігаються з SQL-запитом №2 роботи №3 на тому самому періоді й порозі. `$_id` у `$group` — ключ групи, `$sum` — агрегат, `$match` після групування відповідає `HAVING`, `$sort` — `ORDER BY`. Агрегація повернула 2 рядки, тоді як у предметній області є 4 клуби. Клуб Empty відсутній, бо для нього немає документів-бронювань; повний перелік дає окремий каталог клубів, аналогом якого в попередніх роботах були таблиця `clubs`/вимір `dim_clubs`. Riverside має березневі бронювання, але його сума 200 не проходить поріг `> 250`.

## 9. Схема на читанні

Файл: [schema-on-read.js](schema-on-read.js). У `pcs` вставлено три коректні документи різної форми; поле `monitor_refresh_hz` є у двох із трьох, `gpu_model` — в одному з трьох.

| Команда PostgreSQL | Стовпець | Порожній у таблиці `pcs` |
|---|---|---|
| `ALTER TABLE pcs ADD COLUMN monitor_refresh_hz integer;` | `monitor_refresh_hz` | 4 із 6 рядків |
| `ALTER TABLE pcs ADD COLUMN gpu_model text;` | `gpu_model` | 5 із 6 рядків |

Четвертий тестовий документ містив помилкове поле `seat_numer`. MongoDB його прийняла, але запит за правильним `seat_number` повернув порожній масив; документ видалено, у `pcs` лишилося 3. Це помічає лише застосунок/звіт, який не знаходить значення. PostgreSQL відхилив би `INSERT` із невідомим стовпцем, якщо його не додати до схеми.

## 10. Кеш показника

Файл: [redis-commands.txt](redis-commands.txt). Кешується виручка березня (`revenue:2026-03`): її читають на дашборді, а втрата кешу не руйнує джерело істини — значення повторно обчислюється в PostgreSQL. Ім'я ключа англійською, від загального до конкретного; двокрапка розділяє показник і період. У досліді TTL дорівнює 30 секундам; робочі 300 секунд (5 хвилин) дозволяють часто читати показник, приймаючи невелику затримку оновлення аналітичних даних.

| № | Команда | Фактична відповідь |
|---:|---|---|
| 1 | `SET revenue:2026-03 1540.00` | `OK` |
| 2 | `GET revenue:2026-03` | `"1540.00"` |
| 3 | `TTL revenue:2026-03` | `(integer) -1` |
| 4 | `EXPIRE revenue:2026-03 30` | `(integer) 1` |
| 5 | `TTL revenue:2026-03` | `(integer) 30` |
| 6 | `EXISTS revenue:2026-03` | `(integer) 1` |
| 7 | `GET revenue:2026-03` після очікування 30 секунд | `(nil)` |
| 8 | `TTL revenue:2026-03` | `(integer) -2` |
| 9 | `SET revenue:2026-03 1540.00 EX 300` | `OK` |
| 10 | `INCR reservations:2026-03-12:count` | `(integer) 1` |

`TTL >= 0` — ключ має час до видалення; `-1` — ключ існує без TTL; `-2` — ключа немає. Лапки у форматованій відповіді `GET` показують, що це RESP bulk string (текст), а не числовий тип; додаток має розібрати його як десяткове число перед арифметикою.

| Крок | Команда або дія | Відповідь |
|---|---|---|
| 1. промах | `GET revenue:2026-03` | `(nil)` |
| 2. запит до бази | сума оплат березня у PostgreSQL | `1540.00` |
| 3. запис у кеш | `SET revenue:2026-03 1540.00 EX 300` | `OK` |
| 4. попадання | `GET revenue:2026-03` | `"1540.00"` |

Якщо кеш стерти, область не втрачає дані — значення обчислиться знову.

## 11. Три моделі зберігання

| | Реляційна | Документна | Ключ-значення |
|---|---|---|---|
| Форма | таблиці, рядки, зв'язки | BSON-документи, вкладені поля | ключ і значення |
| Типова операція | транзакційний `JOIN`/запис | читання агрегату та фільтр вкладених полів | `GET`/`SET` за ключем |
| Обіцянка | схема, обмеження, транзакції | гнучка форма й агрегатне читання | простий швидкий доступ за ключем |
| Ціна | joins/міграції схеми | дублювання й валідація в застосунку | обмежені запити й ризик застарілого кешу |

| Модель | Доречна задача | Недоречна задача |
|---|---|---|
| Реляційна | бронювання, оплати, обмеження від подвійного бронювання | кешування одного показника на короткий час |
| Документна | екран бронювання з вкладеними деталями | узгоджене масове оновлення спільних даних клієнта |
| Ключ-значення | кеш виручки або лічильник | складний звіт із довільними зв'язками |

Графові БД доречні для шляхів/сусідства; wide-column — для великих розподілених потоків подій; пошукові — для повнотекстового пошуку. Джерелом істини тут лишається PostgreSQL: там є транзакції та обмеження, що захищають бронювання й оплати. Переносити всю область у документну модель недоцільно: гнучкість не замінює контроль цілісності.

## 12. Протокол запуску середовища

```powershell
docker compose -f compose-nosql.yaml up -d
docker compose -f compose-nosql.yaml ps
```

Вивід `docker compose -f compose-nosql.yaml ps` під час перевірки:

```text
NAME                 SERVICE   STATUS
dbsa-nosql-mongo-1   mongo     Up
dbsa-nosql-redis-1   redis     Up
```

MongoDB `db.runCommand({ ping: 1 })` повернув `{ ok: 1 }`, Redis `PING` — `PONG`. Команди `down -v` не використовувати, якщо потрібно зберегти дані у Docker volumes.
